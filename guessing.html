🛑 IO 傳輸與硬體「燒機」陷阱（極度致命）：
學長名言：「通常 IO 是瓶頸，運算不是瓶頸，改演算法沒用。」
• 症狀：程式沒報錯，但資料一直掉包，或跑一段時間直接崩潰（燒機）。
• 解法 1（位元壓縮）：將多次小資料（如 bool 或小整數）使用位元運算打包進一個 32-bit 整數中，減少傳輸次數。

• 解法 3（手動二分搜）：若無設定檔，找到控制迴圈，將 sleep 時間放大（例如 1ms 改 10ms），測試是否還會掉包。

📦 位元打包（Bit-Packing，IO 瓶頸救星）▼
學長名言：「通常 IO 是瓶頸，運算不是瓶頸，改演算法沒用。」
考點：多次小資料（bool、小整數）→ 用位元運算打包進一個 32-bit，減少傳輸次數。
把 8 個 bool 打包進 uint8_t / 從 uint32_t 拆出多個欄位 
#include <stdint.h>
#include <stdio.h>

// === 打包：8 個 bool → 1 個 uint8_t ===
uint8_t pack_bools(const uint8_t flags[8]) {
    uint8_t packed = 0;
    for (int i = 0; i < 8; i++) {
        if (flags[i]) packed |= (1u << i);
    }
    return packed;
}

// === 拆包：1 個 uint8_t → 8 個 bool ===
void unpack_bools(uint8_t packed, uint8_t out[8]) {
    for (int i = 0; i < 8; i++) {
        out[i] = (packed >> i) & 1u;
    }
}

// === 進階：多個欄位塞進 32-bit（每個欄位固定寬度）===
// 格式：[31:24] id(8) | [23:16] type(8) | [15:8] len(8) | [7:0] flags(8)
uint32_t pack_header(uint8_t id, uint8_t type, uint8_t len, uint8_t flags) {
    return ((uint32_t)id << 24) | ((uint32_t)type << 16)
         | ((uint32_t)len << 8) | (uint32_t)flags;
}

uint8_t get_id(uint32_t h)    { return (h >> 24) & 0xFF; }
uint8_t get_type(uint32_t h)  { return (h >> 16) & 0xFF; }
uint8_t get_len(uint32_t h)   { return (h >> 8)  & 0xFF; }
uint8_t get_flags(uint32_t h) { return  h        & 0xFF; }

int main() {
    uint8_t flags[8] = {1,0,1,1,0,0,1,0};
    uint8_t packed = pack_bools(flags);
    printf("packed = 0x%02X\n", packed); // 0x4D

    uint8_t out[8];
    unpack_bools(packed, out);
    printf("unpack: ");
    for (int i = 0; i < 8; i++) printf("%d ", out[i]);
    printf("\n");

    uint32_t h = pack_header(0x12, 0x34, 0x08, 0xA5);
    printf("header = 0x%08X, id=0x%02X, type=0x%02X, len=%u, flags=0x%02X\n",
           h, get_id(h), get_type(h), get_len(h), get_flags(h));
    return 0;
}
🎯 可能題目
「給你 1000 筆 bool 資料要透過慢速 IO 傳輸，請設計打包格式並寫出 pack/unpack 函式，說明為何能減少傳輸量。」
💡 答案
8 個 bool 原本 8 bytes，打包後 1 byte，IO 量降為 1/8。
🔧 設定檔排查與頻率調整（IO 掉包第一嫌疑）▼
症狀：程式沒報錯，但資料一直掉包或跑久崩潰（燒機）。
第一嫌疑：頻率太高，IO 或硬體吃不消。先找設定檔，不要急著改程式邏輯。
排查 SOP：設定檔 → 迴圈 sleep → 二分搜 
【IO 掉包 / 燒機 排查 SOP】

Step 1. 找設定檔（優先，改設定不改程式）
   $ find . -name "*.json" -o -name "*.yaml" -o -name "*.yml" -o -name "*.toml" -o -name "*.cfg"
   $ grep -rn "frequency\|rate\|freq\|interval\|period\|hz" --include="*.json" --include="*.yaml" .
   找到後把 frequency / rate 調低（例如 1000 → 100），重跑看是否還掉包。

Step 2. 找控制迴圈，放大 sleep
   在程式裡 grep "sleep\|usleep\|nanosleep\|delay\|std::this_thread::sleep"，
   把 sleep 時間放大 10 倍（1ms → 10ms），測試是否還會掉包。

Step 3. 手動二分搜（找不到設定檔時）
   把「每秒傳 N 筆」的 N 逐步砍半：N → N/2 → N/4 ...
   直到不掉包為止，那個 N 就是硬體能吃下的上限。

Step 4. 若以上都沒用 → 才懷疑「單筆資料太大」
   改用位元打包（見「位元打包」區塊）把多筆小資料合併成一個大封包。
🎯 可能題目
「程式在本地跑沒事，在評測環境掉包。請列出至少 3 個排查方向。」
💡 答案
① 找 config 調低 frequency/rate ② 放大迴圈 sleep ③ 位元打包減少單次傳輸量 ④ 檢查 buffer 大小是否 overflow。
🔍 通用二分搜 Debug 法（範圍砍半，快速定位）▼
核心思想：不知道哪裡錯時，把「可能出錯的範圍」砍半，看問題還在不在，重複 log₂(N) 次就能定位。
四種二分搜場景 
【場景 A：資料掉包，找「硬體能吃下的最大頻率」】
  low = 1, high = 10000 (筆/秒)
  while (low < high) {
      mid = (low + high + 1) / 2;
      if (test_at_rate(mid) == OK) low = mid;   // mid 可以
      else high = mid - 1;                       // mid 太多
  }
  printf("硬體上限 = %d 筆/秒\n", low);

【場景 B：程式崩潰，找「哪一行開始錯」】
  在程式碼中段插 printf 印出關鍵變數，
  若中段之前的值正確 → 錯誤在後半；否則在前半。
  重複縮小範圍，通常 5~10 次就能定位到行。

【場景 C：效能太慢，找「哪個函式是瓶頸」】
  在 main 迴圈的不同階段加計時（clock_gettime），
  比較各段耗時，最大的那段就是瓶頸，優先優化它。
  （學長名言印證：通常 IO 是瓶頸，運算不是。）

【場景 D：GitLab 評測失敗，找「哪個 test case 掛」】
  若 OJ 有顯示部分通過，看通過幾個 / 總共幾個，
  先確保最簡單的 case 過，再逐個往上修。
🐙 OJ / GitLab 提交策略（別讓流程吃掉你的分）▼
🛑 致命規則：一次只能跑一個 task。重複提交會把前一個評測「取消」，等於白做。
正確提交 SOP 
【正確提交 SOP：本地驗證 → 一次 push】

Step 1. 本地先編譯、先跑，確認無誤
   $ make clean && make
   $ ./bin/your_program
   用示範 PDF 給的測資或自己造的邊界測資（空輸入、最大值、最小值）驗證。

Step 2. 若 push 卡住（帳密問題）
   $ git config --global credential.helper store
   然後再 push，輸入一次帳密後就會記住。

Step 3. 提交後「不要立刻再 push」
   - 等評測結果回來（可能 pending 10+ 分鐘，後期會塞車）
   - 若失敗，先看 error message，在本地修好，再 push 下一次

Step 4. 若真的需要多次提交
   - 確認前一次評測已「結束」（不是 pending）再 push
   - 若前一次還在跑，你的新 push 可能取消它 → 兩頭空

【千萬不要做的事】
   ✗ 一直 commit 一直 push 想「試試看」
   ✗ 用 merge / rebase 搞版本控制（浪費時間）
   ✗ 在評測 pending 時又 push 同一題

📡 QoS 靜默失敗（ROS 2 最難 debug 的坑）▼
症狀：ros2 topic echo 沒資料，但 ros2 topic info 顯示有 publisher、有 subscriber、topic 名稱完全正確、沒有任何報錯。
QoS 不匹配診斷 
【QoS 靜默失敗診斷 SOP】

Step 1. 看雙方 QoS 是否匹配
   $ ros2 topic info /topic -v
   輸出會列出 Publisher 和 Subscriber 各自的 QoS profile。

Step 2. 對照關鍵欄位
   Reliability:  BEST_EFFORT  vs  RELIABLE
   Durability:   VOLATILE     vs  TRANSIENT_LOCAL
   History:      KEEP_LAST (depth=N) vs KEEP_ALL

Step 3. 常見不匹配組合
   - Publisher 用 BEST_EFFORT（如 /scan 感測器），
     Subscriber 用預設 RELIABLE → 永遠收不到
   - Publisher 用 VOLATILE，Subscriber 晚啟動 →
     錯過啟動時發布一次的地圖 → 收不到
   - depth 太小 + 發布太快 → 中間訊息被丟

Step 4. 修正方式（Python）
   from rclpy.qos import qos_profile_sensor_data
   self.create_subscription(Scan, '/scan', self.cb, qos_profile_sensor_data)
   # qos_profile_sensor_data = BEST_EFFORT + VOLATILE + depth=5

【一句話】QoS 不匹配時，DDS 發現機制看得到彼此，
但不會建立資料連線，且「幾乎沒有事件通知」。
🎯 可能題目
「Nav2 訂閱不到 /scan，ros2 topic info 顯示有 publisher，但 echo 沒資料。列出至少 2 個 QoS 相關原因。」
💡 答案
① Reliability 不匹配（BEST_EFFORT vs RELIABLE）② Durability 不匹配（VOLATILE vs TRANSIENT_LOCAL）③ depth 太小導致丟包。診斷用 ros2 topic info /scan -v。
🚚 DMA 對齊與完成時機（比 count 單位更隱蔽）▼
你已寫的：count 是筆數不是 bytes。
你沒寫的：位址對齊、DMA 完成 ≠ 資料可用、trigger 參數。
🎯 可能題目 A（位址對齊）
「用 DMA_SIZE_32 搬 char buf[100] 到另一個 buffer，DMA 直接 fault 或行為異常。為什麼？」
✅ 正確做法
DMA_SIZE_32 要求來源與目標位址都是 4 的倍數，且長度是 4 的倍數。char buf[100] 的起始位址不保證 4 對齊。解法：__attribute__((aligned(4))) 或改用 DMA_SIZE_8。
🎯 可能題目 B（完成時機）
「DMA 搬完後，dst 前幾個元素是新的、後面是舊值。可能什麼配置問題？」
💡 答案
dma_channel_wait_for_finish_blocking 等的是「DMA 搬完」，若來源是外設（ADC/UART），外設可能還在寫資料。DMA 完成 ≠ 外設寫完。解法：先等外設 data-ready flag，或用外設的 DMA request 觸發模式。
🎯 可能題目 C（trigger 參數）
「dma_channel_configure 配置好了，但 DMA 完全沒動。為什麼？」
✅ 正確做法
最後一個參數 trigger 傳 false 時，通道配置好但不會自動開始，需要另外呼叫 dma_channel_start(chan)。傳 true 才會立即啟動。
對齊 + 啟動完整骨架 
#include "pico/stdlib.h"
#include "hardware/dma.h"

// 確保 4-byte 對齊
uint32_t __attribute__((aligned(4))) src[256];
uint32_t __attribute__((aligned(4))) dst[256];

int chan = dma_claim_unused_channel(true);
dma_channel_config c = dma_channel_get_default_config(chan);
channel_config_set_transfer_data_size(&c, DMA_SIZE_32);  // 要求 4 對齊
channel_config_set_read_increment(&c, true);
channel_config_set_write_increment(&c, true);

// 先配置，trigger=false 不自動啟動
dma_channel_configure(chan, &c, dst, src, 256, false);

// 若來源是外設，先確認 data ready
// while (!peripheral_data_ready()) tight_loop_contents();

// 手動啟動
dma_channel_start(chan);
dma_channel_wait_for_finish_blocking(chan);
⚙️ PIO autopull / autopush 陷阱▼
示範 PDF 說：「echo.pio 假設 OSR 已設定為 autopull」。這句話本身就是考點。
🎯 可能題目 A（autopull 閾值）
「PIO 程式寫對了，但完全不會動。CPU 呼叫 pio_sm_put_blocking 後卡住。可能原因？」
💡 答案
autopull threshold 設 32，但實際只 push 8 bits → OSR 沒「空」到閾值 → autopull 不觸發 → PIO 卡在 out 等資料 → TX FIFO 永不消耗 → CPU 卡在 put_blocking。
🎯 可能題目 B（push 丟資料）
「PIO 送出的資料偶爾少一筆，但沒有報錯。」
💡 答案
push 沒加 block 時，若 RX FIFO 滿，資料會被直接丟棄（不阻塞）。解法：push block 或加大 FIFO 深度 / 提高 CPU 消費速度。
🎯 可能題目 C（autopull 時讀 OSR）
「PIO 用 autopull 收 CPU 資料，但偶爾讀到錯誤的值。」
💡 答案
autopull 是硬體自動從 TX FIFO 補充 OSR，時機和 PIO 程式異步。在 autopull 模式下用 MOV 讀 OSR 是未定義行為（可能讀到殘值或新拉進來的字）。解法：關掉 autopull 手動 pull，或確保在 OUT 之前資料已就位。
PIO autopull 心智模型 
【PIO 資料流與 autopull 開關】

關閉 autopull（手動模式）：
  CPU → pio_sm_put_blocking → TX FIFO
  PIO 程式執行 pull → OSR  ← 程式控制時機
  PIO 程式執行 out  → 取出 OSR 內容到 X/引腳
  → 優點：完全可控
  → 缺點：每個字都要寫 pull 指令

開啟 autopull（自動模式）：
  CPU → pio_sm_put_blocking → TX FIFO
  硬體自動：當 OSR 空了 → 從 TX FIFO 補進 OSR
  PIO 程式執行 out → 直接取 OSR
  → 優點：省 pull 指令
  → 陷阱：
     (1) 程式讀 OSR 內容時機不確定
     (2) threshold 設錯（例如只 push 8 bits 但 threshold=32）→ 永遠不觸發
     (3) PULL 指令在 autopull 且 OSR 滿時是 no-op

【echo.pio 為什麼能運作】
  .program echo
  .wrap_target
    out x, 32   ; 從 OSR 取 32 bits 到 X
    in  x, 32   ; 把 X 推入 ISR
    push        ; ISR → RX FIFO → CPU
  .wrap_target
  前提：OSR 已 autopull 填好資料，否則 out 會 stall。
🔢 getBits / 循環移位（比 SET_BIT 難一檔）▼
你已寫的：SET_BIT / CLEAR_BIT / GET_BIT / GET_BITS。
你沒寫的：循環移位、移位量 ≥ 寬度的 UB、有號整數右移。
getBits / rightRotate / 邊界安全版 
#include <stdint.h>

// === 取 x 的第 p 位起 n 個 bits（p 是起始位索引）===
uint32_t getBits(uint32_t x, int p, int n) {
    return (x >> (p - n + 1)) & ~(~0u << n);
}

// === 向右循環移位（rotate，不是普通 shift）===
uint32_t rightRotate(uint32_t x, int n) {
    int bits = sizeof(x) * 8;   // 32
    n &= (bits - 1);            // 防止 n >= 32（移位量 ≥ 寬度是 UB）
    return (x >> n) | (x << (bits - n));
}

// === 邊界安全遮罩（避開 1u << 32 的 UB）===
uint32_t mask_n_bits(int n) {
    if (n <= 0) return 0;
    if (n >= 32) return 0xFFFFFFFFu;
    return (1u << n) - 1;
}

// === 從資料包取欄位：[31:24] type | [23:8] payload | [7:0] crc ===
uint8_t  get_type(uint32_t pkt)    { return (pkt >> 24) & 0xFF; }
uint16_t get_payload(uint32_t pkt) { return (pkt >> 8)  & 0xFFFF; }
uint8_t  get_crc(uint32_t pkt)     { return  pkt        & 0xFF; }
🎯 可能題目 A（取欄位）
「給定 32-bit 封包，格式 [31:24] type | [23:8] payload | [7:0] crc，寫函式取出 payload。」
🎯 可能題目 B（移位 UB）
「uint32_t x; x << 32 的結果是什麼？」
💡 答案
未定義行為（UB），不是 0。C 標準規定移位量必須小於型別寬度。同理 1u << 32 也是 UB，寫遮罩時要特判 n == 32。
🎯 可能題目 C（負數右移）
「int x = -8; x >> 1 的結果是什麼？」
💡 答案
Implementation-defined（實作定義），大多數編譯器做算術右移得 -4，但 C 標準不保證。要跨平台安全，先轉 unsigned 再移位。
🐕 Watchdog Timer（看門狗，獨立硬體模組）▼
為什麼是新板塊：DMA / PIO / mutex 都是「主動完成功能」的技術。Watchdog 是「被動兜底」——不幫你完成任何事，只負責「程式卡死時把系統拉回來」。這是一個獨立的硬體模組。
Pico SDK Watchdog 骨架 
#include "pico/stdlib.h"
#include "hardware/watchdog.h"

int main() {
    // watchdog_enable(delay_ms, pause_on_debug)
    // delay_ms 最大約 8300（看 bootrom 實作）
    // pause_on_debug=true：用調試器單步時 watchdog 也暫停
    watchdog_enable(2000, true);

    while (1) {
        do_work();           // 可能耗時的操作
        watchdog_update();   // 餵狗：必須在超時前呼叫
        sleep_ms(100);
    }
}
🎯 可能題目 A（餵狗週期）
「程式正常運行但偶爾自動重啟，沒有 crash log。可能原因？」
💡 答案
watchdog 超時時間 < 主循環單次耗時（例如 DMA 等待或大塊 memcpy 超過 2 秒）。程式還沒走到 watchdog_update() 就被重啟。解法：加大超時時間，或在耗時操作中分段餵狗。
🎯 可能題目 B（pause_on_debug）
「用調試器單步執行時，程式一直重啟。為什麼？」
💡 答案
pause_on_debug = false 時，調試器暫停 CPU 但 watchdog 仍在計數，超時就重啟。解法：設為 true，或調試時先停用 watchdog。
🎯 可能題目 C（餵狗位置）
「把 watchdog_update() 放在 if (has_work) 分支裡，某段時間沒工作時程式會重啟。」
💡 答案
餵狗應放在主循環固定位置（每輪必經之路），不能放在條件分支裡。沒工作時分支不執行 → 不餵狗 → 超時重啟。
😴 Sleep / Low-Power Modes（lightsleep vs deepsleep）▼
為什麼是新板塊：「降頻」是降低活動頻率，Sleep 是完全停止活動。兩者在嵌入式系統裡是不同層級的功耗優化。
🎯 可能題目 A（deepsleep 狀態丟失）
「程式進入 deepsleep 喚醒後，main 裡的計數器歸零了。為什麼？」
💡 答案
deepsleep 切斷 RAM 電源，喚醒相當於冷啟動，main 從頭執行，所有變數重新初始化。lightsleep 才保留 RAM 狀態。需要跨 deepsleep 保留的資料要存在 flash / RTC scratch register。
🎯 可能題目 B（lightsleep 醒不來）
「呼叫 lightsleep 後程式完全不動了，也沒有重啟。」
💡 答案
lightsleep 需要配置喚醒源（GPIO 變化、RTC 鬧鐘等），沒配置就永遠醒不來。例如 sleep_goto_sleep_until(&alarm, NULL) 要先用 rtc_set_alarm 設鬧鐘。
🎯 可能題目 C（Watchdog × Sleep）
「進入 sleep 後 watchdog 把系統重啟了。怎麼協調？」
💡 答案
進 sleep 前要嘛先停用 watchdog（watchdog_disable()），要嘛確保 sleep 時間 < watchdog 剩餘時間。喚醒後重新 watchdog_update()。
lightsleep / deepsleep 對照 
【lightsleep vs deepsleep 對照表】

lightsleep：
  - CPU 暫停，RAM 保留，外設狀態保留
  - 喚醒後從「呼叫 sleep 那行」繼續執行
  - 變數值保留
  - 需配置喚醒源（RTC 鬧鐘、GPIO 等）
  - 適合：短暫等待、省電輪詢

deepsleep：
  - 幾乎所有電源切斷，包含 RAM
  - 喚醒後 = 冷啟動，main 從頭執行
  - 變數全部重新初始化
  - 適合：長時間待機（電池供電裝置）
  - 若要保留狀態 → 存在 flash 或 RTC scratch

【lightsleep + RTC 喚醒骨架（Pico SDK）】
  #include "pico/sleep.h"
  #include "hardware/rtc.h"

  datetime_t alarm = {
      .year=2026, .month=11, .day=9,
      .hour=12, .min=0, .sec=5, .dotw=0
  };
  rtc_set_alarm(&alarm);
  sleep_goto_sleep_until(&alarm, NULL);  // 進 lightsleep
  // 喚醒後從這行繼續，變數還在
⚠️ API 規格級坑點（11 條精選）▼
這些都是「不需要歷屆、純從 API 規格就能推出」的坑。每一條都可能包成獨立考題。
1. memory_order 選錯（atomic） 
// ❌ 用 relaxed 當「發布」旗標
atomic_int ready = 0;
int data = 0;

// 執行緒 A
data = 42;
atomic_store_explicit(&ready, 1, memory_order_relaxed);

// 執行緒 B
if (atomic_load_explicit(&ready, memory_order_relaxed)) {
    printf("%d\n", data);  // ❌ 可能讀到 0（data 還沒寫入）
}

// ✅ 寫端 release、讀端 acquire
atomic_store_explicit(&ready, 1, memory_order_release);
// 讀端：
if (atomic_load_explicit(&ready, memory_order_acquire)) { ... }
2. condvar 用同一條導致喚醒錯陣營 
// ❌ 生產者、消費者共用同一條 condvar
pthread_cond_t cond;  // 只有一條

// 生產者
while (count == SIZE) pthread_cond_wait(&cond, &mutex);
// 消費者
while (count == 0)    pthread_cond_wait(&cond, &mutex);

// 問題：signal 可能喚醒「生產者」而該醒的是「消費者」，
// 被喚醒者發現條件不成立又睡回去，真正該醒的卻沒收到通知。

// ✅ 兩條 condvar
pthread_cond_t not_empty, not_full;
3. ring buffer 空/滿歧義 
// ❌ 不用 count，只用 head == tail
int head, tail;
bool is_empty() { return head == tail; }
bool is_full()  { return head == tail; }  // ❌ 兩個條件一樣！

// ✅ 方案 A：保留一個空格（容量實際是 SIZE-1）
bool is_full() { return (tail + 1) % SIZE == head; }

// ✅ 方案 B：加一個額外旗標區分
int count;  // 直接用 count 判空/滿
4. spinlock 在單核退化 
// 單核環境（1 核）：持有 spinlock 的執行緒被排程器換下，
// 等待者會空轉直到時間片用完 → 比 mutex 還差。
// spinlock 只在「多核 + 短臨界區」才划算。
5. 巨集參數沒全加括號 
// ❌
#define SQUARE(x) x*x
SQUARE(a+1)  // 展開成 a+1*a+1，不是 (a+1)*(a+1)

// ✅
#define SQUARE(x) ((x)*(x))
6. 遮罩邊界（1u << 32 是 UB） 
// ❌ n == 32 時 UB
uint32_t mask = (1u << n) - 1;

// ✅ 特判
uint32_t mask_n(int n) {
    if (n <= 0)  return 0;
    if (n >= 32) return 0xFFFFFFFFu;
    return (1u << n) - 1;
}

9. volatile 不是同步機制
